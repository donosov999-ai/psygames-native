## 0. Первое, что делаешь в самый первый заход

### 0.1. 🔴 ВСЕГДА ПЕРЕДАВАЙ `as=<своё имя>`

Твоё имя в TeamOps: `psygames-<раздел>-claude-mac` — например
`psygames-sudoku-claude-mac`. Карточки всех девяти разделов **уже заведены**
администратором доски 06.09.2026, регистрировать себя заново не нужно.

⚠️ **Но без `as=` доска отвечает под именем ТОКЕНА МАШИНЫ (`claude-mac`), где
задач ноль — и пустота читается как «мне ничего не назначено».** Так уже
случилось: чат доложил «inbox пуст», имея девятнадцать задач и шесть срочных.
Это не сбой доски, а неверный адрес вопроса.

```
mcp__teamops__whoami        as="psygames-<раздел>-claude-mac"
mcp__teamops__task_list     as="psygames-<раздел>-claude-mac"  mine=true
mcp__teamops__journal_read  as="psygames-<раздел>-claude-mac"  channel="psygames"
```

Проверь: границы в карточке совпадают с твоим ТЗ? Не совпадают — напиши
`@teamops-claude-mac` в журнал `object=teamops`.

**Дозаполнить СВОЮ карточку можно самому** (`agent_register as=<имя>
name=<имя> …`): дописать `session_id`, `boundaries`, `projects`, `functions`.

⚠️ **А вот СОЗДАТЬ новую личность нельзя — ни себе, ни другому.** Гвард
пропускает создание только от админа доски; формулировка «блокируется только
чужая» неверна, я её сегодня же и поправил. Нужна новая личность — заявка
`@teamops-claude-mac`.

📌 **Образец имени `psygames-<раздел>-claude-mac` — новый**, заведён 06.09.2026.
До него в реестре была схема `<проект>-<движок>-<машина>`, то есть шесть слотов
на весь проект. Новая делит работу ПО ИГРАМ, а не по тому, чем её делают.

### 0.1а. Как сверить СВОЙ адрес доставки

В карточке есть `session_id` — адрес, по которому тебе приходят письма. Сверь
его один раз:

```
get_session "self"        →  local_<uuid>
```

Совпало с карточкой — всё. Не совпало или поле пустое — допиши сам:
`agent_register as=<имя> name=<имя> session_id="local_<uuid>"`.

⚠️ **`deliver` ВОЗВРАЩАЕТ УСПЕХ, НЕ ДОСТАВИВ.** Отправитель видит id письма и
уходит довольный, а состояние `queued` смотрится отдельным вызовом
(`delivery_status`). Замер 07.09.2026: в очереди 15 писем, доставлено НОЛЬ,
старейшему четверо суток. Система теряет молча, и обе стороны считают, что
связь есть. Отправил письмо — проверь `delivery_status`, а лучше продублируй
`journal_add` в канал.

⚠️ **НЕ проверяй адрес «тестовой доставкой».** `deliver` на этой машине
возвращает `state=queued, reason=dispatcher_not_configured`: курьер не поднят,
письмо ложится в очередь и `delivered` не проставит никто. Проверка
«проходит» ОДИНАКОВО при верном и при неверном адресе, то есть не проверяет
ничего. Замер «Памяти и слуха» 06.09.2026, запись 9ab47bc3.

⚠️ **И НЕ бери uuid из имени папки.** Совпадение имени папки с адресом сессии
— случайность; схема это прямо запрещает, и вышел бы мёртвый адрес.
Авторитетный источник один — `get_session "self"`.

## 2. Git

- 🔴 **`git add -A` И `git commit -a` ЗАПРЕЩЕНЫ ОБА.** Только
  `git add <перечисленные свои файлы>` и `git commit` без `-a`.

  ⚠️ **`commit -a` — вторая дверь к той же беде, и её закрыли позже.** Замер
  07.09.2026: коммит `e9ca081e` называется «Маджонг-пробы» (зона «Поиск»), а
  внутри ШЕСТЬ файлов из ТРЁХ зон — два своих маджонговых, три экрана «Памяти и
  слуха» и её же замер лестниц на 98 строк. 114 вставок, из них большая часть
  чужие.

  Три следствия, и ни одно не видно сразу:
  · **работа не потеряна, но потеряно авторство и повод** — через месяц замер
    лестниц «Памяти и слуха» никто не найдёт, он лежит под темой про маджонг;
  · **откатить свою правку теперь нельзя, не задев чужое** — один `revert`
    снесёт 98 чужих строк;
  · **симптома нет вовсе** — сборка зелёная, git молчит, обе стороны уверены,
    что всё нормально. Автор замера узнал об этом не из своего `git log`.

  📌 И перед коммитом — `git status` ГЛАЗАМИ. Появилось чужое — не коммить,
  сказать владельцу.
  06.09.2026 подметание дерева увело работу трёх сессий в чужие коммиты с
  чужими заголовками.
- `git pull --rebase` перед правкой, `git push` сразу после коммита.
- Коммит после КАЖДОГО законченного куска, не «в конце дня». Подпись
  `[Claude·MAC]`.
- **Работа дольше дня — в ВЕТКУ.** Разбор экрана на модули, новая игра,
  переделка лестницы. Мелкое — прямо в `main`. Причина: 06.09.2026 разбор
  `goods-sort` шёл ровно в момент выпуска и дал 14 красных наборов.
- 🔴 **Не оставляй `main` красным на ночь.** Не успеваешь — откати свой кусок,
  а не оставляй сломанным.
- 🔴 **Проба упала по ТАЙМ-АУТУ — сначала посмотри на нагрузку, потом чини.**
  Машина одна на девять чатов. Замер 07.09.2026: `load average 32,7` при
  выпуске — на такой машине проба с лимитом 20-60 секунд падает, ничего не
  сломав.

  ```bash
  uptime            # load average выше ~16 — timing-пробам верить нельзя
  npx jest --runInBand <проба>    # без соперничества между рабочими
  ```

  В тот же заход `chess-blind-interference-screen` покраснела в общем прогоне и
  ПОЗЕЛЕНЕЛА в одиночку — дефекта не было вовсе. ⚠️ Отличать по СЛОВАМ ошибки:
  «Exceeded timeout of N ms» — это про часы, а не про поведение. Расхождение
  `expect` под нагрузкой не появляется.

  📌 Судья в спорном случае — CI: там выделенный раннер и соперничества нет.

- 🔴 **Перед коммитом за тебя теперь смотрит хук** (07.09.2026,
  `scripts/githooks/pre-commit`, включён через `core.hooksPath`). Он гоняет
  `tsc --noEmit` и останавливает коммит, **если ошибка в ТВОЁМ застейдженном
  файле**. Чужая недописанная правка в дереве тебя НЕ блокирует — специально:
  дерево одно на девять чатов, и хук, падающий на соседе, снесли бы за день.

  Стоит около 15 секунд. Сознательно обойти: `git commit --no-verify`.
  Не работает (нет node, tsc не запустился) — коммит проходит: хук страхует, а
  не охраняет.

  Повод: 07.09 координатор ТРИЖДЫ за сутки чинил красный `tsc` в `main` из
  чужих коммитов, и дважды это была одна и та же ошибка, скопированная в
  соседний файл того же коммита. Красный `main` стоил выпуску 2.49.0 отдельного
  захода. ⚠️ Заводишь файл по образцу соседнего — сверяй с ним ПЕРВУЮ строку и
  блок объявлений, а не только тело: три промаха подряд были именно копией.

### 2а. Затёртую работу можно вернуть — до четырёх часов назад

🔴 **`git checkout -- <файл>`, `git restore`, `reset --hard` стирают
незакоммиченное НАСОВСЕМ.** Оно не попадает ни в стеш, ни в объекты, и
`git fsck --lost-found` его не находит. 07.09.2026 так пропала починка чата
«Сортировки» — стёр координатор, проверяя чужой файл.

Поэтому раз в 5 минут снимается снимок всего дерева: launchd-задание
`com.odv999.psygames-safety` → `scripts/safety-snapshot.sh`. Он делает
`git stash create` + `update-ref`, **не трогая ни рабочую копию, ни индекс** —
работающий чат его не замечает. Хранится 48 снимков ≈ 4 часа.

Вернуть своё:

```bash
git for-each-ref refs/safety --sort=-creatordate      # список, свежие сверху
git show "${ref}:frontend/app/games/твоя-игра.tsx"    # ⚠️ ФИГУРНЫЕ СКОБКИ обязательны в zsh
git checkout <ref> -- frontend/app/games/твоя-игра.tsx
```

⚠️ **Снимок — не повод расслабиться в обе стороны.** Он не спасает от того,
что старше четырёх часов, и не отменяет правило «`git status` глазами перед
коммитом». Он спасает от чужой руки, не от своей невнимательности.

## 3. Выпуск — не твой

**Версию не поднимаешь, метку не ставишь, в магазины не заливаешь.** Заливка
приложения целиком — на координаторе.

Причина, дословно от Дениса: «они сделали 5 процентов от приложения и стали
лить, не зная толком 95 процентов?»

Готово — пишешь в канал: «<раздел> зелен, `npx jest <твои пробы>` — N из N».
Метку поставит координатор.

### 3б. 🔴 Во время выпуска — в ветку, не в `main`

**Замер 07.09.2026, зачем это правило появилось.** Координатор трижды прогнал
все 474 набора, чтобы поставить метку 2.49.0. Каждый прогон шёл 3–22 минуты, и
каждый раз к его концу `main` уезжал вперёд: между первым прогоном и меткой
легло **43 чужих коммита**, а проверяемый коммит устаревал ещё до того, как
прогон заканчивался. Пять красных наборов из шести пришли из работы,
закоммиченной в последний час — и каждая починка открывала следующую.

Поэтому: **когда координатор пишет в канал «выпуск, тишина в `main`» —
работаешь в ветке.**

🔴 **ВЕТКА — ЧЕРЕЗ `git worktree`, А НЕ `git switch`.** Дерево у нас ОДНО на
девять чатов: `git switch` в нём переключает его ВСЕМ. Кто переключил — того и
ветка, а остальные восемь начинают коммитить к нему в раздел.

```bash
git worktree add ~/dev/psygames-wt-<раздел> -b <раздел>/<что-делаешь>
cd ~/dev/psygames-wt-<раздел>
ln -s ~/dev/psygames/frontend/node_modules frontend/node_modules   # зависимости общие
# … работа, коммиты как обычно …
git push -u origin <раздел>/<что-делаешь>          # в main НЕ мержишь
```

⚠️ **Замер 07.09.2026, почему это дописано.** Правило §3б я написал утром как
«работайте в ветке», и три чата из четырёх поняли верно — завели свои деревья
`psygames-wt-chess`, `psygames-wt-counting`, `psygames-wt-words`. Четвёртый
понял буквально и сделал `git switch` в общем: `~/dev/psygames` уехал на
`search/ui-geometry`, а мой собственный коммит чуть не лёг в чужой раздел.
Виновато правило, а не чат: в нём стояла команда `git switch -c`.

⚠️ И следствие, которое ловится не сразу: незакоммиченные файлы в общем дереве
на ЧУЖОЙ ветке **блокируют переключение обратно** — `git checkout` откажется
затирать неотслеживаемое. Закончил в своём дереве — прибери за собой.

📌 **Общее дерево `~/dev/psygames` остаётся на `main`.** Это рабочее место
координатора и место, откуда собирается выпуск.

Координатор пишет «метка поставлена, `main` свободен» — тогда:

```bash
git switch main && git pull --rebase
git merge <ветка> && git push
```

⚠️ **Тишина — это не «перестань работать».** Это «перестань двигать то, что я
в эту минуту меряю». Ветка стоит одну команду и ничего не тормозит.

⚠️ И обратное обязательство координатора: объявлять начало и конец тишины
ЯВНО, а не молча. Тишина без объявленного конца — это остановленные чаты.

## 3а. 🔴 Запись о ЧУЖОЙ зоне протухает за часы — в ОБЕ стороны

**Случай 06.09.2026, проверяемый целиком.** В журнале лежала запись
«[чату Сортировки] гейт обложек красный». Чат прочитал её через **7,5 часов** и
пошёл проверять. Оказалось: починилось через **полтора часа** после написания —
все четыре названные пробы зелёные, 31 проверка, обложка закоммичена сборкой
выпуска. То есть шесть часов запись существовала как ложный сигнал и читалась
как текущее состояние.

⚠️ **И правило было дано ОДНОБОКО — на этом наступили те, кто его знал.**
Дословно от чата сортировок: «правило-то я знал, но применял ТОЛЬКО к своим
отчётам; не сработало обратное направление».

Поэтому оно записано в обе стороны:

**Когда ПИШЕШЬ о чужой зоне** — ставь время замера и команду:
> «на 20:35 `npx jest game-thumb-audit` — 3 из 3 красных»,
> а не «гейт обложек красный».

**Когда ЧИТАЕШЬ запись о своей зоне** — сначала посмотри, КОГДА она сделана, и
**перепроверь живьём, прежде чем чинить**. Запись старше пары часов — это не
состояние, а история. Перепроверил и всё зелено — отпишись в журнал, что
запись устарела: следующий не потратит на неё заход.

Это относится и к координатору: половина ложных сигналов дня вышла из моих же
записей чатам.

## 4. Каждая правка несёт три вещи

**Замер ДО числом · гейт, краснеющий на возврате дефекта · замер ПОСЛЕ.**

🔴 **Гейт доказывается мутацией.** Верни дефект — проба обязана покраснеть. Не
покраснела — гейт мерит не то. 06.09.2026 выжившая мутация вскрыла ВТОРОЙ
дефект, прикрытый первым.

🔴 **Гейт проверяет ПОВЕДЕНИЕ, а не исходник.** Проба, ищущая слово в файле,
зеленеет от комментария и краснеет на верном коде. В тот же день гейт обвинил
комментарий, объяснявший его же урок.

🔴 **Отказ требует такого же замера, что и согласие.** Под «нечего брать»,
«дефекта нет», «не подходит» обязаны стоять: чем мерил (команда, файл) · что
получилось (число) · что из отклонённого ВСЁ РАВНО переносится.

🔴 **Цифра в обосновании — не замер.** Если пишешь в комментарий число,
команда, снявшая его, должна быть выполнена ДО того, как комментарий записан.
06.09.2026 в оправдание послабления уехало «0 из 40», а замер дал 36 из 40.

🔴 **Лестницу проверяют ПРОГОНОМ ВСЕХ уровней**, а не сравнением первого с
последним. Ломается на стыке участков — так находили трижды за неделю.

⚠️ **Ярлык, который присваивается за отсутствие результата, не требует замера
и потому прячет плато.** Верхняя ступень «нельзя решить» держалась, пока её не
проверяли; замер показал, что на 25-м уровне трудность равнялась нулю.

## 4а. 🔴 ПОТОЛКОВ НЕТ НИГДЕ

*Слово Дениса 06.09.2026: «никаких потолков нет нигде, всегда можно растить
сложность, вопрос подхода».*

**Сложность можно растить всегда.** Кажется, что различать уровни нечем — это
не свойство игры, а **незаконченный поиск оси**.

«Потолок» подпадает под правило «отказ требует замера». Прежде чем произнести
его, ответь тремя пунктами:
1. **какие оси перебрал** — поимённо по таблице ниже;
2. **почему каждая не подошла** — числом или свойством игры, а не «не подходит»;
3. **как это решили другие** — что нашёл у похожих игр.

Без них «потолок» — не вывод, а прекращение поиска. Отказ дешевле согласия:
чтобы сказать «расти некуда», достаточно НЕ найти; чтобы сказать «вот чем» —
надо найти. Из-за разницы в усилиях он незаметно становится ответом по
умолчанию.

### Десять осей. Объём — только первая и кончается раньше всех

| № | ось | чем растёт |
|---|---|---|
| 1 | объём | больше элементов: цифр, клеток, слов, карточек |
| 2 | скорость | короче показ, короче пауза, жёстче лимит |
| 3 | задержка | пауза МЕЖДУ показом и ответом |
| 4 | интерференция | посторонняя задача между показом и ответом (счёт как в OSPAN) |
| 5 | отвлечение | шум, ложные цели, приманки, которые надо НЕ запомнить |
| 6 | строгость порядка | свободно → по порядку → обратный → сортировка |
| 7 | сходство элементов | созвучные слова, соседние клетки — труднее различать |
| 8 | двойная задача | вторая модальность одновременно (dual n-back) |
| 9 | непредсказуемость | параметр меняется ВНУТРИ партии; правило объявляется после показа |
| 10 | цена ошибки | меньше попыток, штраф за ложную тревогу, серия обнуляется |
| 11 | составность правила | признак, по которому судят, становится составным: не «X», а КРАСНАЯ X; не «стрелка», а «стрелка, а не скобка» |

📍 **Замер, ради которого таблица и написана.** В пяти играх «Объёма памяти»
заняты оси 1 и 2, частично 6 и 8. **Осей 3, 4, 5, 7, 9, 10 нет ни в одной** —
то есть лестницу собирались заканчивать, имея шесть неиспользованных способов
её продолжить. Проверь у себя: скорее всего так же.

### 📌 Пример 10.09.2026: «потолок» оказался ненайденной осью — дважды за один разговор

Оба случая ценны тем, что оси нашлись **не там, где я искал**, и обе идеи —
Дениса, а не мои. Записаны дословно, потому что важен ход мысли, а не итог.

**Случай 1. CPT — я принёс развилку, у которой обе стороны плохи.**
Доложено было так: чтобы растить трудность, надо двигать доли к канону AX-CPT
70/10/10/10 (замер генератора: сейчас AX/AY/BX/BY = 20,0 / 8,6 / 7,7 / 63,6),
но тогда цель перестаёт быть РЕДКОЙ — а на редкости держится вся логика
«пропуск = падение внимания». Выглядит как честная развилка, требующая решения
владельца. На деле это прекращение поиска: перебрана ОДНА ось (доли), и на ней
объявлен тупик.

📌 Слово Дениса: *«можно менять правила, чтобы искал не Х, а другую букву; или
показывать похожее на Х; или задать, что Х должен быть определённого цвета —
например, красный»*.

Три оси вместо развилки, и **редкость цели не трогает ни одна**:

| ось | что растит | чем проверяется |
|---|---|---|
| мишень не всегда X | нельзя играть на автомате, выученном за прошлые партии | удержание правила ЭТОЙ партии |
| буквы, похожие на мишень | различение вместо узнавания | нажатие на двойника = не различил |
| мишень только КРАСНАЯ X | правило становится составным: буква И цвет | нажатие на X не того цвета = не удержал конъюнкцию |

⚠️ И сразу ловушка, видная только замером: список похожих букв подобран ПОД X
(`K Y V W N M` — угловатые). Смените мишень на `K` — и она окажется в списке
собственных двойников, а ось «похожести» тихо выключится. Ось, привязанная к
конкретному значению, обязана пересчитываться вместе с ним.

**Случай 2. Выбор-реакция.** Число альтернатив растёт 2 → 3 → 4 и упирается в
экран: больше кнопок в полосу ответа не влезет.
📌 Слово Дениса: *«можно усложнить, рисуя не стрелки тогда, а иногда вообще
нейтраль или что-то похожее на стрелку — скобку»*.

Опять две оси, и обе **не трогают число кнопок**:
- **похожесть знака** — стрелка → шеврон → скобка: направление по-прежнему
  читается, но узнать его с одного взгляда уже нельзя;
- **нейтраль, на которую жать нельзя** — ловит упреждающее нажатие, то есть не
  только усложняет, а ЗАЩИЩАЕТ меру: без неё быстрый RT может означать не
  скорость, а угадывание до появления стимула.

**Что из этого следует — по замеру кода, а не на глаз.**

| игра | ось 5 отвлечение | ось 7 сходство | ось 9 непредсказуемость |
|---|---|---|---|
| CPT | свободна | **занята частично**: `confusableRatio` есть, но ноль на L1–L10 и растёт лишь с L11 | свободна |
| выбор-реакция | свободна | свободна | свободна |

⚠️ Половина найденного у CPT — не новая ось, а **уже написанная и включённая
только на верхней трети лестницы**. Это отдельный вид «потолка»: механизм есть,
до большинства уровней не доезжает. Прежде чем изобретать ось, проверь греп-ом,
нет ли её уже — и на СКОЛЬКИХ уровнях она включена.

А третья идея Дениса в таблицу не попадала вовсе — добавлена одиннадцатой строкой.

⚠️ **Правило «Конфликта внимания» действует и здесь: доля приманок — не ручка
сложности.** Растить надо ПОХОЖЕСТЬ и СОСТАВНОСТЬ правила, а долю нейтралей и
долю целей держать замороженными. Иначе повторится дефект, который в этом
разделе чинился семь раз: ручка уровня начинает сжимать ту самую величину, ради
которой проба и существует.

### ⚠️ Не путай три разные вещи — лечатся по-разному

| что видишь | это | что делать |
|---|---|---|
| соседние уровни **одинаковы** | 🔴 дефект: лестница обещает рост и не даёт | найти ось |
| уровни различаются, но дальние никто не пройдёт | ✅ норма: длинный хвост | не трогать |
| уровень **недостижим** | ✅ решено гистерезисом: 3 провала → уровень −1 | не трогать |

Склеить первые две и обрезать обе — та самая ошибка, из-за которой правило и
появилось.

### ⚠️ Не мерь тренажёр линейкой клинического теста

Тесту потолок у нормы нужен: он меряет в узком диапазоне. **Тренажёру с
лидербордом нужен хвост** — иначе все упираются в одно число, таблица рекордов
превращается в ничью, а человеку, тренировавшемуся полгода, некуда расти.
Норма (7±2 цифры, 5±2 клетки) — это про НЕтренированных, а приложение тренирует
ровно это.

### Где смотреть чужие решения

Ключевое слово — **`staircase` / `adaptive`**: так в психометрике зовётся
подстройка сложности, и она обычно вынесена отдельной функцией или конфигом.
Смотри не как выглядит, а **какие параметры крутит КРОМЕ объёма** и как решён
верх: обрезали, зациклили или перешли на другую ось.

Порядок поиска — по дешевизне: соседняя игра нашего же приложения (их 71) →
`donosov999-ai/forks-catalog` → GitHub и npm **по именам файлов и синонимам**
(искали `sudoku` и не нашли 40 генераторов, потому что файл зовётся `solo.c`) →
🟢 не нужны ли ДАННЫЕ вместо кода: нормы по возрастам, откалиброванные наборы
стимулов, корпуса с рейтингом трудности.

⚠️ Лицензию проверяй ФАЙЛОМ, а не бейджем: у Тэтхэма файл зовётся `LICENCE`
по-британски, детектор его не видит.

### Как отчитаться, если ось всё-таки не нашлась

> «Оси 3, 4, 7 не подходят, потому что <свойство + число>. Оси 5, 9, 10
> применимы, но требуют <что>. Смотрел: `<сосед>`, forks-catalog, GitHub по
> `<запросы>`, нашёл `<репо>` — там верх решён так-то. Беру ось N.»

А не «дальше расти некуда».

⚠️ **И поправка к вашим ТЗ:** в них написано «назови числом, где рост
кончается». Формулировка приглашает объявить потолок. Читать её надо так:
**назови, где рост кончается ПО НЫНЕШНЕЙ ОСИ, и какую берёшь следующей.**

## 5а. 🔴 Завёл файл ядра — поставь штамп и пересобери реестр В ТОМ ЖЕ КОММИТЕ

За 06–07.09 два гейта общего слоя падали ЧЕТЫРЕЖДЫ, и каждый раз по одной
причине: раздел завёл новый файл ядра, а штамп и реестр остались прежними.
Чинил их каждый раз координатор — то есть ваша минута экономии стоила чужого
захода и однажды остановила выпуск.

**Штамп — ПЕРВОЙ строкой файла, по форме:**

```
/* psygames-<игра>-<модуль> · VER 1 · <дата> */
```

⚠️ Ярлык начинается с имени СВОЕЙ игры: у файла в `src/games/anagrams/` он
`psygames-anagrams-…`, а не `psygames-anagram-…`. И это `psygames-<игра>-…`, а
не `<игра>/<файл>` — гейт `core-module-stamp` проверяет обе половины.

**Реестр редакций пересобирается командой:**

```
cd frontend && node scripts/gen-game-versions.mjs
```

Результат (`src/constants/gameVersions.ts`) идёт в ТОТ ЖЕ коммит, что и новый
файл. Гейт `game-versions-registry` сверяет собранное заново с закоммиченным.

**Проверка перед push — три команды, полминуты:**

```
npx tsc --noEmit
npx jest core-module-stamp game-versions-registry module-games-guard
node scripts/lint-ratchet.mjs
```

⚠️ И `import { readFileSync } from 'fs'` в пробе роняет `tsc`: в tsconfig
проекта нет типов узла. В пробах — `require` с точечным `eslint-disable` и
причиной, как у соседей.
