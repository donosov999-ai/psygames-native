## Как этим пользуется игрок

1. В приложении: Настройки → облачное сохранение → вход по почте → явное
   включение сохранения своей истории. Ручной «Перенос прогресса» с длинным
   кодом — другая, резервная функция, для этого маршрута он не нужен.
2. На экране облака: «Поддержка прогресса Судоку». Выбрать свой профиль-режим
   и дорожку: Полегче / Обычная / Пожёстче. Разрешить поддержку на **24 часа**.
   Лимит сервера — не более72ч. Каждое изменение выдаёт новую ревизию.
3. Оператор видит только действующее разрешение и минимальный статус Судоку:
   профиль, дорожку, уровень/best и наличие сохранённой партии, без самой доски.
4. Оператор отправляет «открыть уровень не ниже80». Игрок нажимает
   «Проверить исправления» → «Применить исправление» в том же приложении.
   Файлы и коды между устройствами не передаются.
5. При старой сохранённой партии нужно согласие на новую доску. Исходные байты
   партии остаются в локальной резервной записи. Отмена не удаляет партию.

Этот первый маршрут — доставка через облако с явным принятием исправления,
не скрытое дистанционное управление телефоном и не автоматический новый ход.

## Ограничения и защита данных

- Одно облачное согласие не даёт разрешения на поддержку. Разрешение отдельно,
  ограничено Sudoku + owner + app + profile + road + revision + временем.
- Нет универсального JSON-патча, скачивания snapshots или доступа к покупкам,
  кошельку, имени питомца, дневнику и данным других приложений.
- Только `unlock_at_least`: два reached-level ключа меняются монотонно
  (`max(local, target)` с наследованием дорожек). Победа, очки, награды,
  сессия и звёзды не создаются. Выше180 сервер не принимает.
- Операторская очередь — только через серверный service credential из
  разрешённого локального хранилища. Этот ключ не попадает в Flutter, Git,
  бэкап, журналы или сообщения. В приложение входит только publishable key.
- Серверный `applied` — сообщение клиента о применении, не независимая
  проверка настоящего телефона. Статус уровня также сообщён приложением.
- RLS/session guard скрывают чужие строки; у anon нет доступа. Service role
  не получает прямой доступ к новым таблицам: только узкие RPC.
- Queue идемпотентна по owner/requestUUID. Не создавать новый UUID для
  автоматического повтора потерянного ответа. Повтор с другими аргументами
  отвергается. Убывающий queuefloor также отвергается.

## Запись, обрыв и восстановление

Прежде чем менять два ключа, клиент сохраняет owner/issuer-журнал с точным
запросом и исходной доской. Журнал локальный, исключён из облачного бэкапа.
Подтверждение сервера идёт **после** локального завершения, не раньше.
Даже терминальный `completed`/`acked` повторно подтверждается платформой перед
допуском к игре: кэш мог обновиться после неудачной записи. Отдельная проба с
разными cache/disk моделирует отказ completed → повтор выхода → новый board →
перезапуск. Независимое P1-замечание ревью по этому сценарию исправлено и закрыто
повторным чтением источников; обычные реальный-device/OS границы остаются.

Состояния: `prepared → completed → acked`. Только `prepared` может ещё менять
игровые ключи. `completed` может дождаться ACK позже, не трогая новую доску.
Список ограничен100; незавершённые записи не вытесняются ради новых.

`recoverSudokuSupportWrites` выполняется перед игровыми экранами при старте,
даже с выключенным облаком. Это завершение уже принятого локального намерения,
а не новое облачное разрешение: сеть, серверный ACK и новые запросы отсутствуют.
При изменившейся доске/повреждённом журнале — остановка до игры, без удаления
новой партии. При выходе из поддержки: suspend → дождаться отправленных
записей → закончить локальное восстановление → разрешить возврат в игру.

`SharedState.set/remove` теперь проверяют boolean-ответ платформы, а не только
кэш SharedPreferences. Отказ платформы не выдаётся за подтверждённую запись.
Это проверка прикладного протокола, **не** гарантия fsync/неубиваемости ОС.

## Команды оператора

Из корня указанного выше checkout. Только после согласия игрока; текущий
разбор задачи **не** разрешает пробовать эти команды на Вале до её согласия.
Почта и игровые идентификаторы не должны попадать в публичные журналы.

Перед запуском оператор задаёт `PSY_SUPPORT_CREDENTIAL_FILE` как абсолютный
путь к разрешённой локальной конфигурации. В репозитории нет значения этого
пути и нет значения ключа. При отсутствии файла/другом проекте — отказ, без
неявного поиска или вывода содержимого. Команды не предназначены для клиента.

```sh
node scripts/cloud-support/remote-sudoku.mjs lookup '<почта игрока>'
node scripts/cloud-support/remote-sudoku.mjs queue '<почта игрока>' women normal 80 '<request UUID>' 'Progression recovery'
```

Вторая команда по умолчанию — dry-run. После проверки exact profile/road,
уровня, ревизии и причины добавить `--confirm`. При потере ответа не повторять
вслепую: сохранить и проверить тот же request UUID/аргументы. `queued` не
означает, что телефон получил или применил исправление.
